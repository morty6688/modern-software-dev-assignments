# 三个仓库的 Agent Readiness 对比总结

## 3. 哪些维度的缺口最突出？

### 3.1 最一致的缺口：最终产物验证

在三份报告检查的 CI 范围内，**3/3 仓库都缺少最终发布包的独立消费验证**，但不能把它们视为同等严重：

- vn.py 的 [CI:44](D:/project/self/test/vnpy/.github/workflows/pythonapp.yml:44)止于 `uv build`。
- FastAPI 的 [发行包 CI:26](D:/project/self/test/cs146s/fastapi/.github/workflows/test-redistribute.yml:26)已经验证 sdist，并从 sdist 构建 wheel，只差进一步安装最终 wheel 并验证。
- htmx 的 [CI:18](D:/project/self/test/cs146s/htmx/.github/workflows/ci.yml:18)只运行 `npm ci` 和 `npm test`，尚未把已有 dist 构建接入这一流程。

这说明源码测试和最终交付物之间仍有验证空白。智能体改动包资源、导出入口、类型声明或构建脚本时，现有源码测试可能无法发现交付问题。这是对验证覆盖范围的推断，不是声称已经发生发布故障。

### 3.2 共同模式：验证能力没有完全转化为可靠反馈

三个仓库的测试维度都有明确改进项，但问题类型不同：

| 仓库 | 证据 | 对智能体工作的可能影响 |
|---|---|---|
| vn.py | [CI:18](D:/project/self/test/vnpy/.github/workflows/pythonapp.yml:18)只有 Windows/Python 3.13；未配置覆盖率报告 | 智能体难以知道测试未覆盖的代码及其他声明支持环境是否受影响。 |
| FastAPI | [test.yml:259](D:/project/self/test/cs146s/fastapi/.github/workflows/test.yml:259)用 xargs 执行 pytest，并把非零状态统一描述为预期的 base 失败 | 环境或采集故障可能被误读为“测试证明修复必要”，形成错误证据。 |
| htmx | [package.json:34](D:/project/self/test/cs146s/htmx/package.json:34)的 npm test 仅测 Chromium；完整跨浏览器命令未进入 CI | 修改可能通过默认验证，但 Firefox/WebKit 行为仍未验证。 |

这里不能简单按“测试工具多寡”排序。FastAPI 的基础设施最完整，但仍可能因结果解释逻辑而产生错误判断。

### 3.3 文档与环境入口：三个样本都有改进空间

vn.py 的依赖分散和格式化说明不一致，htmx 的测试入口与文档不一致，FastAPI 的本地贡献指引主要跳转外部页面。这三类问题都会增加智能体搜索、推断和选错命令的机会。FastAPI 的外部指引未完整验证，因此这里只能确认本地入口不足，不能断言完整贡献文档缺失。

### 3.4 不能据此宣布“安全维度失败最多”

vn.py 与 htmx 的安全自动化配置缺口较集中，但分支保护、托管扫描和实际网络暴露都没有验证。缺少配置文件不等于托管能力关闭。FastAPI 已有工作流安全扫描和依赖更新，不能将三个样本概括为“普遍没有安全治理”。

原始报告还存在分类上的注意点：FastAPI 可观测性表中一行虽然标为“缺失”，内容实际是“未发现必须补充的框架级遥测入口”。本总结按其语义理解为**未确认缺失项**，不把它计作失败；原报告未在本次改写。

## 6. 评估框架与本次方法的局限

1. **文件存在不等于机制有效。** 有测试脚本不代表 CI 调用了它；有回归任务不代表它正确区分失败原因；有 CODEOWNERS 不代表分支规则强制评审。
2. **相同标准对不同项目的重要性不同。** htmx 的浏览器错误事件比内置服务端仪表盘更贴近职责；vn.py 的资金操作和线程健康边界不能仅用一般日志配置代替。
3. **Unknown 不能压成失败或通过。** 远程治理、部署安全、实际测试结果都没有证据；把这些计入失败会惩罚不可见性，把它们计入通过又会制造信心。
4. **重复计数会放大问题。** htmx 的 CI/文档不一致同时影响 Testing 和 Documentation；随机条件影响 Testing 和 Observability，应按一个根因处理。缺失项条数不适合作为排名依据。
5. **质量门槛需要解释范围。** FastAPI 的 100% 是配置门槛，且存在统计范围和排除项；本次没有执行，不是测得的覆盖率。复杂度门禁未启用也不证明代码复杂度高。
6. **需要评估安全默认行为和操作副作用。** vn.py 的账户/配置隔离，htmx 的浏览器下载与 dist 生成，FastAPI 的动态依赖安装都会影响智能体执行过程。清晰的边界与可重放记录值得单独检查。
7. **静态就绪度不是效果评测。** 本次没有统一任务、相同模型、相同时间预算下的对照实验，无法量化智能体完成率、成本或出错率。
8. **样本数量和选取方式限制外推。** 三个仓库是便利样本，其中一个包含本地学习改进；不能推导语言、维护模式或整个开源生态的普遍规律。

## 7. 总结与后续验证范围

从现有静态证据看，FastAPI 的验证自动化配置最完整，htmx 已有可扩展的浏览器验证基础，vn.py 已有明确的领域模型和本地操作边界。三者共同需要关注的是从“有工具”到“能稳定、正确地获得验证证据”的过程。

后续若要验证这些判断，应在隔离环境中分别复现环境安装、核心测试和最终包消费，再选取可比较的小修改任务记录成功率、重试次数、耗时及额外人工干预。vn.py 的历史测试记录不替代本次复验；远程设置和实际运行结果在获得新证据前继续保持 Unknown。
