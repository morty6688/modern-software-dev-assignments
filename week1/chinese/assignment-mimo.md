# 第 1 周：剖析一次真实 MiMo CLI 会话的调用轨迹（MiMo 2.6 版）

> 本文是[原中文作业说明](assignment.md)的 MiMo 适配版，使用官方 MiMo Code CLI（命令为 `mimo`）和 MiMo 2.6 模型。保留原作业的五部分任务、证据要求及 100 分评分结构，将客户端配置、请求字段和专属机制替换为 MiMo 中对应的实现。配套使用[MiMo 版报告模板](writeup-mimo.md)。

## 作业概述

本周，你将让一次真实的 MiMo CLI 会话通过代理运行，使用 MiMo 2.6 完成编程任务，捕获它实际发送的 HTTP 请求，并对这些请求进行**剖析**。你无需开发新系统，而是要深入阅读他人用于生产环境的系统，细致到能够看出其中的设计决策。

区分两层：**MiMo CLI** 负责组织提示词、注册和执行工具、管理会话；**MiMo 2.6** 是接收请求并生成响应的模型。分析时不要把客户端的设计直接归因于模型。

### 学习目标

- **追踪**生产级编程智能体的一次真实编程会话，理解其调用结构。
- **识别**在一项有一定复杂度的编程任务中，提示词、工具模式（schema）和模型响应如何相互配合。
- **反思**在构建自己的定制智能体时，哪些行为值得借鉴，哪些需要调整。

## 学习材料

- **[MiMo Code 安装与接入](https://mimo.mi.com/docs/zh-CN/tokenplan/integration/mimo-code)**：官方 CLI 的安装、登录及模型选择。
- **[MiMo Code 模型与供应商配置](https://mimo.xiaomi.com/mimocode/models-provider)**、**[配置文件](https://mimo.xiaomi.com/mimocode/config-files)**与**[配置覆盖规则](https://mimo.xiaomi.com/mimocode/config-overrides)**：自定义接口地址、模型和项目级设置。

- **[mitmproxy 反向代理说明](https://docs.mitmproxy.org/stable/concepts/modes/#reverse-proxy)**：捕获与转发模型请求的原理。

## 环境配置

**前提条件：MiMo Code CLI 与 MiMo API 凭证**。按照官方文档安装 CLI；Windows 可使用 `npm install -g @mimo-ai/cli`。运行 `mimo --version` 确认安装成功，并在报告中记录版本号。

本实验采用 MiMo CLI 官方文档中的自定义供应商配置，将请求送入代理。请在 [MiMo 开放平台](https://platform.xiaomimimo.com/) 获取可用的 API Key，并在启动 CLI 的终端中准备环境变量 `MIMO_API_KEY`；配置文件只引用该变量，不填写真实密钥。示例使用按量付费接口及 `mimo-v2.6-pro`。若使用 MiMo 2.6 的其他型号，在配置中一致替换模型 ID，并在报告中记录完整名称。

**1. 安装 mitmproxy：**

- **macOS**：`brew install --cask mitmproxy`。
- **Windows**：运行 [mitmproxy.org](https://mitmproxy.org/) 提供的安装程序，它会将 `mitmweb` 加入 `PATH`。
- **Linux 或其他任意平台**：运行 `pip install mitmproxy`；如果已创建课程 conda 环境，请在该环境中安装。

**2. 以反向代理模式启动：**

```text
mitmweb --listen-host 127.0.0.1 --listen-port 58888 --web-open-browser --mode reverse:https://api.xiaomimimo.com -w session.flows
```

发送到 `127.0.0.1:58888` 的流量会被转发到 MiMo API；检查界面会在 `http://localhost:8081` 打开。反向代理模式让你将 MiMo CLI 指向一个使用普通 HTTP 的本地地址，因此无需安装 CA 证书。`-w session.flows` 会将每条网络交互记录（flow）保存到磁盘；请在**任何 Git 仓库之外**的目录运行此命令，避免意外提交捕获文件。上面的命令写成一行，可直接用于 PowerShell 或 Bash。

若使用 Token Plan，请根据平台给出的 OpenAI 兼容 Base URL，将反向代理的目标改为该地址的域名部分，并使用配套的 Token Plan Key。例如，平台地址为 `https://token-plan-cn.xiaomimimo.com/v1` 时，代理目标为 `reverse:https://token-plan-cn.xiaomimimo.com`。本地配置中的 `/v1` 保留；不要把 `/v1` 重复拼接到代理目标中。

**3. 将 MiMo CLI 指向代理**：在第一部分要使用的仓库根目录创建**项目级** `mimocode.json`。如果已有该文件，请先备份，再合并以下设置：

```json
{
  "$schema": "https://mimo.xiaomi.com/mimocode/config.json",
  "model": "mimo-capture/mimo-v2.6-pro",
  "small_model": "mimo-capture/mimo-v2.6-pro",
  "provider": {
    "mimo-capture": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "MiMo Capture",
      "options": {
        "baseURL": "http://127.0.0.1:58888/v1",
        "headers": {
          "api-key": "{env:MIMO_API_KEY}"
        }
      },
      "models": {
        "mimo-v2.6-pro": {
          "name": "MiMo V2.6 Pro"
        }
      }
    }
  }
}
```

`mimo-capture` 是此处自定义的供应商标识；真正发送给 API 的模型 ID 是 `mimo-v2.6-pro`。`small_model` 也指向同一供应商，便于捕获标题生成等辅助请求；统计时应将它们与编程任务请求区分。若已有自定义智能体单独指定了模型，也要记录并检查其请求是否经过代理。

> ⚠️ **只在实验项目中设置本地代理地址，不要写入全局 MiMo 配置。** 否则，其他会话也可能进入捕获范围，并在 `mitmweb` 停止后无法正常调用。不要把真实 API Key 写入项目配置或报告。

**4. 验证**：在实验仓库中启动一个新会话：

```text
mimo --model mimo-capture/mimo-v2.6-pro
```

发送一条简单请求，确认 mitmweb 中出现成功的 `POST /v1/chat/completions`，且请求体中的 `model` 为 `mimo-v2.6-pro`。再让智能体读取一个普通项目文件，确认后续请求包含工具定义、调用记录和工具结果。只有这些检查通过，才开始正式捕获；CLI 能启动或界面显示模型名称，不能单独证明流量已走代理。接口路径或载荷若与示例不同，先核对 CLI 版本和生效配置，并在报告中记录实际格式。

**5. 作业结束后**：退出实验会话，恢复原有 `mimocode.json`，或移除本次新增的 `mimo-capture` 供应商及指向它的 `model`、`small_model` 设置，再停止 `mitmweb`。如果文件完全为本实验新建，可以删除该文件。清除本次临时设置的密钥环境变量。

## 第一部分：捕获一次会话（15 分）

在代理下运行**一次**会话，并满足以下全部四项要求：

1. **涉及多个文件**：至少操作两个文件。
2. **至少失败一次**：需要出现一次错误恢复过程。故意让某个测试失败，是可靠的触发方式。
3. **任务足够长，需要制定计划**：智能体应给出明确计划，而不是只执行一次工具调用。计划可以采用任务列表、计划模式或计划文件的形式。
4. **使用你自己的仓库**：使用临时实验项目，而不是本作业仓库。

如果不想自己设计任务，可以参考以下**任务示例**：

- 删除一个被其他模块导入的函数，然后要求 MiMo CLI 恢复完整功能并让测试通过。
- 为一个小型 Web 应用添加端点和测试，然后要求它在某个你尚未安装的依赖版本下让整个测试套件通过。
- 重命名一个模块，让它更新所有导入语句，然后运行 lint 检查和测试。
- 要求实现一个需要使用陌生库的功能，使智能体必须先查阅 API 才能编写代码。

在 mitmweb 界面中，选择 `POST /v1/chat/completions` 记录，将其**请求体**下载为 JSON。为相关请求编号（如 R001、R002），并保留对应响应或流式响应记录，便于关联模型发出的工具调用与下一次请求中的工具结果。将这些文件保存在本地。你无需提交它们，但后续各部分都会根据这些文件中的证据评分，因此请保留足以支撑答案的记录。

分析时可从 `messages` 中的 `system`／`developer` 消息定位系统指令，从 `tools[].function` 查看工具定义，从助手消息的 `tool_calls` 与工具消息的 `tool_call_id` 关联调用和结果。若 CLI 将部分工具或提醒编码在文本中，也应指出实际位置，不要只统计标准字段。以捕获内容为准，CLI 导出的聊天记录可以辅助定位，但不能替代真实 HTTP 请求。

如果 mitmweb 会话终止，可以继续使用已保存的 `session.flows` 文件：运行 `mitmweb -r session.flows` 重新打开。

### ⚠️ 对引用内容进行脱敏

捕获内容包含你自己的源代码、文件路径和凭据。除了你有意引用到 `writeup.md` 中的摘录，其他捕获内容都不应进入仓库。

- 不要将 `session.flows` 放进任何 Git 仓库。

## 第二部分：注释系统提示词（25 分）

将 `messages` 中所有 `role: "system"`／`role: "developer"` 的消息，以及其他承载客户端指令的内容拆分为不同章节。说明项目规则（如被加载的 `AGENTS.md`）最终出现在哪里；不存在的字段无需补造。对每一部分回答：**它希望促成什么行为，又在防范什么失效模式？** 这里需要的是分析注释，而不是内容概括。

至少覆盖以下方面：

- **结构**：主要章节、排列顺序，以及为何这样排序。
- **语气与详略程度**：具体哪些措辞控制了回复长度和格式，以及为什么值得为这些指令消耗 token。
- **何时不应行动**：破坏性操作的执行门槛、范围限制、拒绝条件。
- **环境上下文**：智能体被告知了哪些机器、仓库和会话信息，以及这些信息位于请求中的什么位置。

然后，专门分析**运行时提醒与动态上下文注入**（对应原作业的 `<system-reminder>` 题目）：它们出现在哪里（系统指令、用户消息、工具结果或其他位置；请引用示例）？你能用证据说明的两种不同用途是什么？为什么要在对话中途注入，而不是在开头一次性说明？可检查模式切换、任务状态、权限提示、上下文恢复等场景，但不要预设 MiMo 必须采用某个标签或机制。若未观察到足够的实例，明确写出检查过的请求范围，并以官方文档或对应版本源码为依据，将补充分析标为 `[INFERRED]`，不能把缺失项当作已观察到的行为。

## 第三部分：注释工具设计（25 分）

**工具清单：用数字，而非泛泛描述。** 一共有多少可用工具？请按内置工具、MCP 提供的工具、延迟加载／可搜索工具分类统计。注明不同请求之间工具集合是否发生变化，以及是什么触发了变化。好的答案应类似于*“第一个请求中有 117 个工具：35 个内置工具，82 个来自三个 MCP 服务器的工具”*，而不是*“有很多可用工具”*。

上面的数字仅为格式示例。MiMo 如有插件或自定义工具，单独列出；未配置 MCP 或未观察到延迟加载时，如实填写 0 或“未观察到”。来源分类与加载方式可能重叠，计算总数时按工具去重，并注明统计的是当前请求中可见的工具，还是通过搜索可进一步获得的工具。

**设计分析。** 选择**两个**工具，分别从接口设计角度分析：

- 展示工具模式中相关的部分。
- 为什么采用这一组参数？哪些必填，哪些可选，哪些有意不对外暴露？
- 工具描述在防范什么问题？成熟智能体的工具描述，在很大程度上是历次踩坑积累的经验。找出一句因为模型反复做错某件事才会存在的话，并指出那种错误行为。
- 该工具有意*不做*什么？这对周边系统的设计意味着什么？

请选择两个有明显差异的工具。选择两个文件操作工具说服力较弱；将文件工具与编排工具搭配，或选择一个具有特殊失败约定的工具，会更有分析价值。

## 第四部分：基于证据的行为分析（25 分）

根据你自己的调用轨迹回答每个问题。每个答案都必须**引用证据**（具体哪个请求、消息索引、工具调用），并**标注 `[OBSERVED]` 或 `[INFERRED]`**：`[OBSERVED]` 表示“观察所得”，你能在捕获记录中直接指出；`[INFERRED]` 表示“推断所得”，你是根据定义推理，并未实际观察到该行为。两者都可以接受，但不能标错；未标注的答案不得分。

- **错误恢复**：完整梳理一次失败及恢复过程。智能体看到了什么，接下来尝试了什么，恢复用了多少轮？请逐字引用原文。
- **规划**：它来自工具、提示词指令、自发形成的行为，还是几者结合？什么证据能区分这些情况？
- **计划与任务状态**：计划如何创建和推进？每一轮模型能看到哪些任务状态信息，它们位于请求中的什么位置？
- **子智能体**：智能体何时委派任务？子智能体收到什么信息，又返回什么？（如果会话没有触发子智能体，诚实标注为 `[INFERRED]` 也可以。）
- **上下文管理**：随着会话增长，请求载荷发生了什么变化？较早的对话轮次在后续请求中如何表示？

## 第五部分：反思（10 分）
