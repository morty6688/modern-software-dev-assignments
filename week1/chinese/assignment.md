# 第 1 周：剖析一次真实 Claude Code 会话的调用轨迹

## 作业概述

本周，你将让一次真实的 Claude Code 会话通过代理运行，捕获它实际发送的 HTTP 请求，并对这些请求进行**剖析**。你无需开发新系统，而是要深入阅读他人用于生产环境的系统，细致到能够看出其中的设计决策。

### 学习目标

- **追踪**生产级编程智能体的一次真实编程会话，理解其调用结构。
- **识别**在一项有一定复杂度的编程任务中，提示词、工具模式（schema）和模型响应如何相互配合。
- **反思**在构建自己的定制智能体时，哪些行为值得借鉴，哪些需要调整。

## 学习材料

- **[拦截 Claude Code 请求](https://www.ai.moda/en/blog/tutorial-intercepting-claude-code-requests)**：本作业所依据的技术。请先阅读。
- **[Anthropic Messages API 参考文档](https://docs.claude.com/en/api/messages)**：你将阅读的请求结构（`system`、`tools`、`messages`）。
- **[Claude Code 设置参考文档](https://docs.claude.com/en/docs/claude-code/settings)**：用户级（`~/.claude/settings.json`）和项目级（`.claude/settings.json`）设置的工作方式。

## 环境配置

**前提条件：Claude Code**。斯坦福通过 SUNet ID 提供 Claude Code 访问权限。如果尚未激活账户，请先[申请访问权限](https://uit.stanford.edu/service/claude)，然后[安装并登录](https://code.claude.com/docs/en/setup)。账户获批并完成安装后，运行 `claude --version` 确认安装成功，并在报告中记录版本号。

**1. 安装 mitmproxy：**

- **macOS**：`brew install --cask mitmproxy`。
- **Windows**：运行 [mitmproxy.org](https://mitmproxy.org/) 提供的安装程序，它会将 `mitmweb` 加入 `PATH`。
- **Linux 或其他任意平台**：运行 `pip install mitmproxy`；如果已创建课程 conda 环境，请在该环境中安装。

**2. 以反向代理模式启动：**

```bash
mitmweb --listen-host 127.0.0.1 --listen-port 58888 \
        --web-open-browser --mode reverse:https://api.anthropic.com \
        -w session.flows
```

发送到 `127.0.0.1:58888` 的流量会被转发到真实 API；检查界面会在 `http://localhost:8081` 打开。反向代理模式让你将 Claude Code 指向一个使用普通 HTTP 的本地地址，因此无需安装 CA 证书。`-w session.flows` 会将每条网络交互记录（flow）保存到磁盘；请在**任何 Git 仓库之外**的目录运行此命令，避免意外提交捕获文件。

**3. 将 Claude Code 指向代理**：在第一部分要使用的仓库中，创建**项目级** `.claude/settings.json`：

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://127.0.0.1:58888",
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

> ⚠️ **不要将这些设置放入 `~/.claude/settings.json`！** 否则，你机器上的所有 Claude Code 会话都会进入此次捕获范围（而且停止 `mitmweb` 后，这些会话将无法正常工作）。

**4. 验证**：启动一个新的 `claude` 会话，发送任意内容，确认 mitmweb 中出现一条 `POST /v1/messages` 记录。

**5. 作业结束后**：完成作业后，删除该仓库中的 `.claude/settings.json`（或其中的 `env` 块），并停止 `mitmweb`。

## 第一部分：捕获一次会话（15 分）

在代理下运行**一次**会话，并满足以下全部四项要求：

1. **涉及多个文件**：至少操作两个文件。
2. **至少失败一次**：需要出现一次错误恢复过程。故意让某个测试失败，是可靠的触发方式。
3. **任务足够长，需要制定计划**：智能体应给出明确计划，而不是只执行一次工具调用。计划可以采用任务列表、计划模式或计划文件的形式。
4. **使用你自己的仓库**：使用临时实验项目，而不是本作业仓库。

如果不想自己设计任务，可以参考以下**任务示例**：

- 删除一个被其他模块导入的函数，然后要求 Claude 恢复完整功能并让测试通过。
- 为一个小型 Web 应用添加端点和测试，然后要求它在某个你尚未安装的依赖版本下让整个测试套件通过。
- 重命名一个模块，让它更新所有导入语句，然后运行 lint 检查和测试。
- 要求实现一个需要使用陌生库的功能，使智能体必须先查阅 API 才能编写代码。

在 mitmweb 界面中，选择一条 `POST /v1/messages` 记录，将其**请求体**下载为 JSON。将这些文件保存在本地。你无需提交它们，但后续各部分都会根据这些文件中的证据评分，因此请保留足以支撑答案的记录。

如果 mitmweb 会话终止，可以继续使用已保存的 `session.flows` 文件：运行 `mitmweb -r session.flows` 重新打开。

### ⚠️ 对引用内容进行脱敏

捕获内容包含你自己的源代码、文件路径和凭据。除了你有意引用到 `writeup.md` 中的摘录，其他捕获内容都不应进入仓库。

- 绝不要粘贴原始网络交互记录或 HTTP 请求头，因为 `x-api-key` / `authorization` 就在这些位置。
- **请求体也可能包含秘密信息。** 智能体读取的任何内容（`.env`、配置文件、命令输出）都会在 `messages` 中再次出现。引用工具结果前，请先检查其中的内容。
- 不要将 `session.flows` 放进任何 Git 仓库。
- 对引文中的私密内容使用清晰可见的标记进行脱敏（如 `[REDACTED: internal hostname]`，表示内部主机名已隐去），不要悄悄删除。
- 如果某段摘录无法在保留原意的同时完成脱敏，请改用一个可随时丢弃的临时仓库重新捕获。

## 第二部分：注释系统提示词（25 分）

将 `system` 块以及所有 `role: "system"` 的消息拆分为不同章节。对每一部分回答：**它希望促成什么行为，又在防范什么失效模式？** 这里需要的是分析注释，而不是内容概括。

至少覆盖以下方面：

- **结构**：主要章节、排列顺序，以及为何这样排序。
- **语气与详略程度**：具体哪些措辞控制了回复长度和格式，以及为什么值得为这些指令消耗 token。
- **何时不应行动**：破坏性操作的执行门槛、范围限制、拒绝条件。
- **环境上下文**：智能体被告知了哪些机器、仓库和会话信息，以及这些信息位于请求中的什么位置。

然后，专门分析 `<system-reminder>`：它们出现在哪里（`system` 块、消息中，还是两者都有；请引用示例）？你能用证据说明的两种不同用途是什么？为什么要在对话中途注入，而不是在开头一次性说明？

## 第三部分：注释工具设计（25 分）

**工具清单：用数字，而非泛泛描述。** 一共有多少可用工具？请按内置工具、MCP 提供的工具、延迟加载／可搜索工具分类统计。注明不同请求之间工具集合是否发生变化，以及是什么触发了变化。好的答案应类似于*“第一个请求中有 117 个工具：35 个内置工具，82 个来自三个 MCP 服务器的工具”*，而不是*“有很多可用工具”*。

**设计分析。** 选择**两个**工具，分别从接口设计角度分析：

- 展示工具模式中相关的部分。
- 为什么采用这一组参数？哪些必填，哪些可选，哪些有意不对外暴露？
- 工具描述在防范什么问题？成熟智能体的工具描述，在很大程度上是历次踩坑积累的经验。找出一句因为模型反复做错某件事才会存在的话，并指出那种错误行为。
- 该工具有意*不做*什么？这对周边系统的设计意味着什么？

请选择两个有明显差异的工具。选择两个文件操作工具说服力较弱；将文件工具与编排工具搭配，或选择一个具有特殊失败约定的工具，会更有分析价值。

## 第四部分：基于证据的行为分析（25 分）

根据你自己的调用轨迹回答每个问题。每个答案都必须**引用证据**（具体哪个请求、消息索引、工具调用），并**标注 `[OBSERVED]` 或 `[INFERRED]`**：`[OBSERVED]` 表示“观察所得”，你能在捕获记录中直接指出；`[INFERRED]` 表示“推断所得”，你是根据定义推理，并未实际观察到该行为。两者都可以接受，但不能标错；未标注的答案不得分。

- **错误恢复**：完整梳理一次失败及恢复过程。智能体看到了什么，接下来尝试了什么，恢复用了多少轮？请逐字引用原文。
- **规划**：它来自工具、提示词指令、自发形成的行为，还是几者结合？什么证据能区分这些情况？
- **计划与任务状态**：计划如何创建和推进？每一轮模型能看到哪些任务状态信息，它们位于请求中的什么位置？
- **子智能体**：智能体何时委派任务？子智能体收到什么信息，又返回什么？（如果会话没有触发子智能体，诚实标注为 `[INFERRED]` 也可以。）
- **上下文管理**：随着会话增长，请求载荷发生了什么变化？较早的对话轮次在后续请求中如何表示？

## 第五部分：反思（10 分）

最多一页：写出**两个你会借鉴的设计决策**及其各自解决的问题；**一个你会采用不同做法的决策**，并认真分析现有做法为何可能存在；以及**此次调用轨迹让你改变的一点**，即今后日常使用编程智能体时，你会如何调整引导方式。
