## 补丁复盘

| 运行 | 存量投递是怎样处理的 |
| --- | --- |
| Terra | API 启动时扫描持久化历史，为重复事件优先发出 `event.cancelled`，并用迁移标记记录处理进度。Router 持久保存取消状态，清理排队或已租出的投递，并阻止后续补发重新创建。Worker 发出请求前通过 `/queue/check` 复查租约。 |
| Luna 原配置 | API 改用数据库做 24 小时内的幂等去重。Router 依靠新 v4 事件消息里的幂等键来识别重复。旧版待发布消息缺少该字段，已写入 Router 的旧事件按 ID 重放时会提前返回。 |
| Luna 通用验证 | 日志确认代理读取了第一版 `AGENTS.md`。Router 能处理取消消息，但 API 只有在收到同一幂等键的新请求时才会发出该消息。新增单测直接调用 Router 的取消分支，公开回放为 3/3，通过这些检查仍无法证明升级时会主动触发取消。 |
| Luna 实际入口验收 | 日志中的实际入口复现是重启 API 后重发同键请求。补丁给待发布的 v3 消息补充幂等键，并在同键请求到来时附带历史重复项。已经发布并留在 Router 队列里的旧任务仍缺少一个在新版启动时主动触发的取消步骤。 |

相同的五个失败场景涉及旧任务待重试、原件已成功投递、多笔支付重复、发送中的重复任务，以及新版启动两次。补丁对照表明，三轮 Luna 都集中解决了收到新请求或消息后的去重和取消，升级前已存在的队列仍有覆盖缺口。这是静态分析，未逐个隔离验证五个失败的根因。

两版 `AGENTS.md` 各跑了一次，对照只说明本次改动未提高修复分。影响报告的统计数字曾从 5/6 改进到 6/6，下一轮又回到 5/6。Terra 的数据库查询不带时间窗口，跨 24 小时复用同一幂等键的行为未单独验证。
